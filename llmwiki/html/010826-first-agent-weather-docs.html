Vì sao đây là một "agent", không phải một script

Theo concepts/agent.md, một agent tận dụng LLM để tự quản lý việc thực thi workflow và có quyền truy cập tools để hành động — ở dạng nền tảng nhất, nó gồm đúng ba thành phần dưới đây.

Hai đặc điểm cốt lõi của agent

  • Dùng LLM để quản lý thực thi + ra quyết định của workflow, biết khi nào hoàn tất hoặc cần dừng lại chuyển quyền cho người dùng.
  • Có quyền truy cập nhiều tools để vừa thu thập ngữ cảnh vừa hành động, luôn trong guardrails đã định.

Weather agent thể hiện điều đó thế nào

  • Model chọn có nên gọi tool và diễn giải kết quả tool trả về.
  • Tool duy nhất get_weather là nguồn sự thật — instructions cấm agent tự bịa số liệu.
  • Nhánh "không có dữ liệu" (NO_DATA:) là một guardrail nhỏ, xử lý edge case rõ ràng.

01 · Model

Chọn model đúng độ khó của tác vụ

Model cung cấp năng lực suy luận và ra quyết định cho agent. Không phải tác vụ nào cũng cần model mạnh nhất — weather agent chỉ cần phân loại intent + gọi đúng tool, nên gpt-4o-mini là đủ.

Ba nguyên tắc chọn model

  • Thiết lập evals để tạo baseline hiệu năng.
  • Tập trung đạt độ chính xác bằng model tốt nhất hiện có trước.
  • Tối ưu chi phí/độ trễ bằng cách hạ xuống model nhỏ hơn khi vẫn đạt kết quả chấp nhận được.

Trong code

weather_agent = Agent(
    name="Weather agent",
    model="gpt-4o-mini",
    instructions=INSTRUCTIONS,
    tools=[get_weather],
)

02 · Tools

get_weather — tool duy nhất, tách khỏi SDK để test được

Tools mở rộng năng lực agent bằng API. Điểm quyết định trong build: tách logic thuần _get_weather_impl khỏi wrapper @function_tool, để unit test chạy offline không cần OPENAI_API_KEY.

Ba loại tools (theo tài liệu ingest)

  • Data — truy xuất ngữ cảnh (weather agent: get_weather tra dữ liệu mock).
  • Action — tương tác hệ thống để hành động (không dùng trong MVP này).
  • Orchestration — agent làm tool cho agent khác (ngoài phạm vi MVP, xem manager-pattern).

Vì sao tách hàm thuần

  • _get_weather_impl không phụ thuộc SDK → test được bằng pytest thuần, không cần API key.
  • @function_tool chỉ là wrapper mỏng gọi lại hàm thuần — giữ một nguồn logic duy nhất.
  • Bug thật bắt được nhờ cách tách này: .lower() không bỏ dấu tiếng Việt, lộ ra ngay khi verify offline.

03 · Instructions

Guardrail bằng lời: không bao giờ bịa số liệu

Instructions là hướng dẫn + guardrail xác định cách agent hành xử. Điểm mấu chốt của weather agent: bắt buộc gọi tool trước khi trả lời, và xử lý rõ ràng nhánh không có dữ liệu.

Thực hành tốt đã áp dụng

  • Định nghĩa hành động rõ ràng: "luôn gọi tool trước khi trả lời".
  • Bao quát edge case: nhánh NO_DATA: có hướng dẫn xử lý riêng, không để model tự suy diễn.
  • Cấm rõ ràng hành vi không mong muốn: "không bao giờ tự bịa nhiệt độ hay tình trạng thời tiết".

INSTRUCTIONS thật trong agent.py

"Bạn là weather agent. Luôn gọi tool get_weather
để lấy dữ liệu trước khi trả lời — không bao giờ
tự bịa nhiệt độ hay tình trạng thời tiết.
Nếu kết quả tool bắt đầu bằng 'NO_DATA:', hãy nói
rõ với người dùng là bạn không có dữ liệu thời tiết
cho thành phố đó, và đừng đoán số liệu thay thế."

04 · Quy trình

propose → gate → plan → build, và 4 lỗi thật gặp phải

Toàn bộ do Claude Code thực hiện trong một phiên, gate qua AskUserQuestion thay vì orchestration đầy đủ vì đây là quyết định kiến trúc + code nền tảng đầu tiên của repo.

4 lỗi thật, không phải giả định trước

  • Đụng tên package — thư mục agents/ trùng tên import của SDK openai-agents → đổi thành demo_agents/.
  • Python 3.9 thiếu union syntax X | None mà SDK dùng nội bộ → thêm eval_type_backport.
  • .lower() không bỏ dấu tiếng Việt — key dict phải giữ dấu để khớp input đã normalize.
  • ModuleNotFoundError khi chạy script trực tiếp — Python không tự thêm repo root vào sys.path → chuyển sang python -m demo_agents.weather_agent.run.
