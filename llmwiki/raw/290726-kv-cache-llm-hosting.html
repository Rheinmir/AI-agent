00 · Kiến trúc Agent

Luồng dữ liệu qua 7 layer, đọc trái sang phải như một quy trình

Dữ liệu chảy: Data Collector → Memory → Context → Model Hosting → Tools, rồi Harness (khung nét đứt) lặp lại vòng này tới khi xong việc. Evaluation đứng riêng bên dưới, nối bằng dây nét đứt, vì nó chỉ quan sát chứ không nằm trong luồng xử lý. Tắt thử một layer bên dưới để xem quy trình "thọt" ở đâu.

✅ Đủ 7/7 layer — agent usable trong ngân sách latency đã tính.

✅ Đủ 7/7 layer — agent phản hồi đúng, nhớ ngữ cảnh, thực thi được hành động, và tự giám sát chất lượng.

Ngân sách latency — thứ thật sự quyết định "usable"

Latency_tổng ≈ Context_assembly(~ms) + Memory_retrieval(20-100ms) + [Model_TTFT + N_token×decode_time] × N_vòng_lặp(Harness) + Tool_call_time × N_lần_gọi_tool

So với ngưỡng "chấp nhận được" (vd <3s cho chat tương tác, <10-15s cho tác vụ agentic nhiều bước). Model_TTFT/decode_time (mục 01) chỉ là MỘT số hạng — Harness nhân số vòng lặp và Tools cộng latency gọi ngoài thường lớn hơn phần model nhiều lần.

01 · Model Hosting Layer

Lõi trong cùng: chạy được model — chi tiết đã phân tích, gọn lại để mở khi cần

Đây là layer duy nhất cần GPU. 6 layer còn lại bên dưới chạy trên hạ tầng CPU thường — nhưng vẫn cộng dồn vào latency tổng. Bấm để mở từng phần.

4 biểu đồ trực quan — VRAM, đánh đổi tok/s, active params, benchmark

Ngân sách VRAM 1024GB: weight vs KV cache còn lại

11 model có weight ≤ 1.1TB, sắp theo weight tăng dần. Đường đứt nét = ranh giới ngân sách 1024GB.

Weight (fp16) KV cache còn lại Vượt ngân sách

Đánh đổi: model to hơn lấy được gì, mất gì — token/s ước lượng

Cùng thứ tự hàng (weight tăng dần) như chart phía trên. Vì sao ra số này (chứng minh, không phải áng chừng): decode bị giới hạn bởi băng thông đọc weight (memory-bandwidth-bound) — mỗi token sinh ra phải đọc lại toàn bộ active-weight từ HBM một lần, không phải giới hạn bởi FLOPs (nguồn: phân tích inference-scaling MLSYS·IM + hướng dẫn triển khai vLLM/Anyscale). Công thức: tok/s ≈ Bandwidth_tong / (Active_params_B × bytes_elem). Chứng minh bằng số thật (Qwen3-235B-A22B): cụm 8×H200 (141GB/GPU, 4.8TB/s/GPU) → băng thông tổng = 8×4.800 = 38.400GB/s; active=22B, fp16=2byte → 38.400/(22×2) = 38.400/44 ≈ 873 tok/s — khớp đúng số hiển thị trong chart bên dưới cho model này.

Đây là số SINGLE-STREAM (1 user dùng riêng), không phải throughput chia đều cho nhiều user. Với nhiều user đồng thời, continuous batching giúp 1 lần đọc weight phục vụ nhiều sequence cùng lúc → throughput TỔNG có thể tăng gần tuyến tính theo batch size (chưa nghẽn, vẫn memory-bound). Nhưng vượt một ngưỡng batch size, hệ thống chuyển sang compute-bound (giới hạn FLOPs) → throughput tổng KHÔNG tăng thêm nữa dù thêm user → đây mới là điểm "nghẽn" thật, mỗi user mới làm chậm trung bình của tất cả.

Đánh đổi không tuyến tính: weight KHÔNG quyết định tốc độ — tỷ lệ active/total (độ "sparse" MoE) mới quyết định. Cohere Command A+ (436GB, active 25B) chỉ ~768 tok/s, chậm hơn MiniMax M2 (460GB, active 10B) đạt ~1920 tok/s.

Chi phí suy luận thật: active params/token

14 model có active-param đã xác nhận (loại Kimi K3, Qwen3.8-Max vì chưa verified). Sắp tăng dần.

Benchmark: Artificial Analysis Intelligence Index

Chỉ 4 model có số điểm xác nhận CÙNG phiên bản index (v4.1, cùng nguồn) nên so được — model khác dùng thang đo khác nên KHÔNG đưa vào để tránh so sánh lệch chuẩn.

GLM-5.2 dẫn đầu benchmark nhưng nằm ở tier "quá lớn" — điểm số này KHÔNG phản ánh việc có vừa ngân sách VRAM hay không.

Infra cost layer này: 1 cụm GPU (8×H100/H200 tuỳ model, xem checklist mục 2) — layer DUY NHẤT trong 7 layer cần GPU. 6 layer còn lại dưới đây chạy trên CPU thường, nhưng vẫn cộng vào latency tổng.

02 · Tools Layer

Tay chân của agent — không có nó, agent chỉ nói suông

Định nghĩa và thực thi các "hành động" agent có thể gọi: search web, chạy code, gọi API nội bộ, đọc/ghi file/database.

Bọc như thế nào

Model chỉ SINH RA text mô tả "muốn gọi tool X với tham số Y". Tools layer là code THẬT nằm ngoài model, nhận yêu cầu đó, thực thi thật, trả kết quả về cho vòng lặp tiếp theo (do Harness điều phối).

Tại sao quan trọng

Đây là ranh giới giữa "chatbot nói chuyện" và "agent làm việc thật". Model mạnh cỡ nào cũng chỉ dừng ở gợi ý nếu không có tay chân để thực thi.

Nếu bỏ layer này — hệ thống ngố thế nào

Bạn nhờ agent "gửi email nhắc nhóm dự án X deadline mai" → nó chỉ trả lời "Đây là nội dung email bạn có thể copy..." rồi DỪNG LẠI — không gửi được, dù nó "biết" phải làm gì.

Infra cost: mỗi tool = 1 service/endpoint riêng (có thể cần sandbox chạy code cách ly, proxy gọi API ngoài). Latency tool call cộng TRỰC TIẾP vào tổng thời gian phản hồi — tool gọi API bên thứ 3 chậm là nguyên nhân phổ biến nhất khiến agent "nhanh trên giấy, chậm khi chạy thật".

03 · Memory Layer

Trí nhớ ngắn/dài hạn — không có nó, agent mất trí mỗi lượt

Lưu trạng thái hội thoại ngắn hạn (trong session) và dài hạn (giữa các session) — lịch sử chat, fact đã học, preference user.

Bọc như thế nào

Đọc/ghi mỗi lượt — đứng giữa Data Collector (nạp dữ liệu ngoài, mục 05) và Context layer (lắp vào prompt, mục 04).

Tại sao quan trọng

Không có memory, agent "mất trí nhớ" hoàn toàn mỗi lần gọi mới — không nhớ ngữ cảnh hội thoại trước, không cá nhân hoá được.

Nếu bỏ layer này — hệ thống ngố thế nào

Tin nhắn 1: "Tôi tên Minh, làm kế toán." Tin nhắn 3: "Vậy phòng tôi xử lý được yêu cầu này không?" → Agent hỏi lại: "Bạn làm phòng ban nào ạ?" — quên sạch 2 câu vừa nói.

Infra cost: 1 session store (Redis, <5ms), 1 lần gọi vector DB retrieval (20-100ms tuỳ index size) — cộng trực tiếp vào latency mỗi turn.

04 · Context/Instruction Layer

Lắp ráp prompt — phần lớn "agent ngu" thực ra là lỗi ở đây

Lắp ráp prompt thật gửi vào model mỗi lượt — system instruction, kết quả Memory, tool schema, lịch sử rút gọn, đúng thứ tự, đúng token budget.

Bọc như thế nào

Lớp "biên dịch" ngay trước khi gọi model — nhận input từ Memory + Tools + Harness, xuất ra 1 prompt/messages array cuối cùng.

Tại sao quan trọng

Prompt lắp sai thứ tự/thiếu context = model trả lời sai dù model mạnh cỡ nào — không phải lỗi model, mà lỗi assembly.

Nếu bỏ layer này (hoặc lắp sai) — hệ thống ngố thế nào

Agent có đủ tool, đủ trí nhớ, đủ dữ liệu — nhưng lắp tài liệu 50 trang TRƯỚC câu hỏi thật của bạn, khiến model "quên" mất câu hỏi ở dưới cùng và trả lời lạc đề, dù mọi input đều đúng và đầy đủ.

Infra cost: thường KHÔNG cần service riêng — chạy như code trong Harness (vài ms CPU). Không tốn container riêng, nhưng tốn token budget (ảnh hưởng chi phí + latency gián tiếp qua độ dài prompt).

05 · Data Collector Layer

Nạp dữ liệu ngoài — không có nó, agent không biết gì riêng của bạn

Thu thập, làm sạch, index dữ liệu bên ngoài (tài liệu nội bộ, web, API, database công ty) để nạp vào kho tri thức cho agent tra cứu (RAG).

Bọc như thế nào

Chạy độc lập, theo lịch (cron/batch) hoặc streaming — KHÔNG nằm trong đường request-response trực tiếp; kết quả đổ vào vector DB mà Memory layer đọc.

Tại sao quan trọng

Agent không tự "biết" dữ liệu riêng của tổ chức — thiếu layer này, nó chỉ dựa kiến thức train sẵn, dễ trả lời sai/lỗi thời với domain-specific info.

Nếu bỏ layer này — hệ thống ngố thế nào

Hỏi "chính sách nghỉ phép công ty mình là gì?" → Agent trả lời chung chung kiểu Google, hoặc BỊA ra một chính sách nghe hợp lý nhưng SAI hoàn toàn, vì chưa từng "đọc" tài liệu nội bộ của bạn.

Infra cost: 1 service ETL/ingestion (worker, CPU-only), 1 vector database (Qdrant/Milvus/pgvector). KHÔNG nằm trong request-time trực tiếp, trừ khi làm real-time crawling.

06 · Harness Layer

Vòng lặp điều phối — "não" quyết định agent thông minh hay không

Vòng lặp chính (think → act → observe → repeat) — quyết định khi nào gọi model, khi nào gọi tool, khi nào dừng, xử lý lỗi/retry.

Bọc như thế nào

Layer NGOÀI CÙNG về mặt điều khiển — ôm toàn bộ Model/Tools/Memory/Context bên trong, chạy như 1 process điều phối, tự nó không sinh câu trả lời.

Tại sao quan trọng

Độc lập với model mạnh cỡ nào — harness kém thì agent vẫn "ngu" theo nghĩa không biết dừng đúng lúc hay chọn đúng bước.

Nếu bỏ layer này (hoặc yếu) — hệ thống ngố thế nào

Agent cần 3 bước để trả lời (tra dữ liệu → tính toán → viết báo cáo) nhưng không có ai điều phối vòng lặp, nên nó dừng lại sau bước 1 và trả lời luôn dữ liệu thô, hoặc lặp vô hạn không biết khi nào nên dừng.

Infra cost: 1 service điều phối (CPU-only, có thể serverless/lightweight) — nhưng mỗi bước lặp cộng thêm 1 lần gọi model → latency NHÂN theo số vòng lặp trung bình, không phải cộng 1 lần.

07 · Evaluation Layer

Cảm biến sức khoẻ — chạy ngoài luồng, không chặn latency user thật

Đo chất lượng đầu ra (đúng/sai, hữu ích, an toàn), theo dõi regression, chấm điểm tự động hoặc người gác.

Bọc như thế nào

Chạy SONG SONG/SAU (out-of-band) — không nằm trong đường request-response trực tiếp; quan sát toàn hệ thống từ ngoài. Vòng ngoài cùng, nét đứt trong sơ đồ mục 00.

Tại sao quan trọng

Không có eval, không biết agent có đang xuống cấp (đổi version model, đổi prompt, tool lỗi) cho đến khi user complain.

Nếu bỏ layer này — hệ thống ngố thế nào

Tuần trước agent trả lời đúng 95%. Tuần này ai đó đổi version model hoặc sửa prompt, độ chính xác rớt còn 60% — nhưng không ai biết, vì không có gì đo lường liên tục. Đến khi khách hàng complain hàng loạt mới phát hiện ra.

Infra cost: 1 pipeline eval riêng (batch job hoặc LLM-as-judge — tốn thêm GPU/API call NHƯNG offline, không cộng vào latency request thật).
